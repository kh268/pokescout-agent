# Shared card and research storage contract v1.0

This is the target storage contract for the hackathon integration. It defines
where records live, their identity and which component can change them. Existing
behavior and additions requiring implementation are distinguished below.
It supplements `Research_Agent_Contract.md` and
`Decision_Trading_Agent_Contract.md`; it does not silently change their current
Python or HTTP schemas.

## Scope and locations

Single user, one local application instance, Japanese cards and integer JPY
amounts. Run commands from the repository root, or pass the same absolute
database/data paths to every process. Never let different working directories
silently create different collections.

```text
data/
  collection.sqlite3              # authoritative inventory and transactional state
  images/<sha256>.<extension>      # retained original uploaded image bytes
  evidence/<sha256>.txt            # retained source text, UTF-8
  research/<run_id>/
    request.json                  # immutable request snapshot
    events.jsonl                  # append-only run events
    report.json                   # immutable completed/partial/failed report
  decisions/<decision_id>.json     # immutable decision and input references
  drafts/<draft_id>-<revision>.json
```

Only `collection.sqlite3` and its existing tables are implemented today. The
image/evidence registry, shared artifact layout and production action/cash
records below are additions to implement. Experimental `experiments/sc/logs`
can remain where it is; import a run explicitly instead of moving or relabeling
historical evidence. Existing `runs/` and bundled `evidence/` are not rewritten.

`data/` is already ignored by Git. Commit schemas, synthetic examples and tests;
do not commit the operational database, uploaded photos, credentials or personal
collection data. Back up the database and referenced files together using a
consistent SQLite backup, not a raw copy of an active database alone.

## Common record rules

- New records carry `schema_version`, a stable ID and a UTC ISO-8601 timestamp
  including its timezone. Display may use Asia/Tokyo; storage uses UTC.
- Operational identifiers are opaque and generated by the application. Preserve
  existing `copy-*` IDs. Card names, URLs and file paths are not physical-copy IDs.
- A missing value is `null`/unknown, never zero, free shipping or perfect
  condition. Monetary values are nonnegative integer JPY; estimated values carry
  their basis and are not treated as confirmed cash.
- New files use UTF-8. File references are paths relative to `data/`, resolved
  within that directory. File names are generated from IDs or hashes, never
  directly from user-supplied names or URLs.
- Hashes are lowercase SHA-256 of the exact saved bytes. Retain provider/request
  IDs where available, but never API keys, authorization headers or login state.
- Completed reports, decisions, evidence and draft revisions are immutable.
  Write to a temporary file and rename atomically; do not overwrite an existing
  final artifact. Corrections create a new revision/run with a predecessor ref.

## Card identity versus a physical copy

There is no required master catalog for the hackathon. Each owned copy retains
its confirmed card snapshot, using `cards.py`'s existing fields:

| Field | Meaning |
| --- | --- |
| `name`, `set`, `number`, `language`, `variant` | Confirmed printing identity; all required for owned-copy registration. |
| `year`, `brand` | Optional confirmed metadata. |
| `presentation` | `raw` or `slabbed`. |
| `grader`, `grade`, `grade_text`, `cert_number`, `qualifiers` | Observed/confirmed slab information; raw cards cannot receive invented slab grades. |
| `defects` | Disclosed or observed defects, preserved verbatim. |
| `uncertainties` | Unresolved fields; confirmation must resolve material identity uncertainty. |

Use the existing `identity_key()` and grading-cohort rules when adapting into
the existing planner. Names or card numbers alone do not uniquely identify a
printing. A future catalog ID is optional metadata and must not replace the
confirmed identity without a reviewed migration.

Two physical cards with the same printing are **two owned-copy records**. The
same printing may also appear in many listings; a listing is not an owned copy.

## Owned copies: existing authoritative storage

`collection.py` owns the `copies` table in `collection.sqlite3`:

| Existing column | Contract |
| --- | --- |
| `id` | Unique physical-copy ID. |
| `card` | JSON snapshot validated by `cards.py`, not arbitrary model output. |
| `image_hash` | Existing optional primary-image hash; not an image file or full image registry. |
| `cost` | Known acquisition cost in JPY, or null when unknown. |
| `allow_sale` | Explicit permission flag, false by default; not authorization for a particular trade. |
| `state` | Currently created as `owned`; lifecycle extensions require implementation. |
| `created` | Creation timestamp. |

Register through the collection API after user confirmation. Agents must not
write SQL to bypass validation. Inventory corrections and transitions need a
revision/event before they can be used in referenced decisions; preserve the
old snapshot so earlier decisions remain explainable.

The existing unique image-hash check detects exact-image reuse, not whether
two different photos show the same physical card. It must not merge physical
copies automatically. A deliberate second-copy confirmation is a separate
intake operation; do not bypass the current duplicate check without adding that
operation explicitly.

## Images: additive registry

Retain original bytes under `data/images/`. Validate supported format and size
before registration. An `assets` registry stores `sha256` (primary key), relative
path, MIME type, byte count and creation time. A `copy_assets` relation stores
`copy_id`, `sha256`, role (`front`, `back`, `slab_label`, `detail`, `other`) and
attachment time. One copy may have several images; image identity is not copy
identity. Both are additive tables owned by the collection/intake layer.

Persist the file atomically before committing its registry/reference rows.
Failed database writes may leave an unreferenced file, which is safe to clean
up later; never create a database reference to a file that was not saved.
No silent deletion of referenced images or source evidence.

## Condition: preserve evidence before normalization

Raw-card condition is separate from printing identity and slab grade. New
condition records use this shape for both owned-copy and listing evidence:

| Field | Contract |
| --- | --- |
| `condition_raw` | Exact shop/user wording, such as `A−`, or null. |
| `condition_normalized` | `near_mint`, `unused`, `played`, `damaged` or `unknown`. |
| `condition_basis` | `user_confirmed`, `seller_claim`, `shop_mapping` or `unknown`. |
| `source_ref`, `observed_at`, `evidence_refs` | Provenance for the wording and any inspection. |
| `mapping_version` | Versioned shop-specific mapping ID, or null. |

There is **no universal A/A−/B-to-near-mint mapping**. Preserve a shop's original
grade; use `unknown` until an explicit shop mapping or user confirmation supports
a normalized category. Seller claims remain seller claims. `unused` does not
prove defect-free or near-mint condition. Never infer a numeric grade for a raw
card. Keep disclosed defects even when a normalized condition is accepted.

For owned cards, persist append-only `copy_condition_history` rows keyed by a
condition-record ID and `copy_id`, with a revision and the fields above. Reference
the selected revision from a decision's collection snapshot. This is an additive
table; do not insert extra fields into `copies.card` and assume the current
validator will preserve them.

Current research `condition` strings remain unchanged in the report. An adapter
creates this richer condition record and passes the normalized category to
`decisions.py` only when supported. Unknown raw-card condition does not satisfy
the planner's allowed-condition filter.

## Research runs and listing observations

The authoritative research result is the immutable `ResearchReport` for its
`run_id`. Save its request, events and final report under `data/research/`.
The research agent owns these writes; decision/trading components read them.
An optional database index may point to report files; it is not another editable
copy of the observations.

- Scope listing identity by marketplace and native listing ID, or a canonical
  URL when no native ID is available. Retain the original source URL too.
- Identify one observation by `(run_id, listing_id, observed_at)`. Reinspection
  creates a new observation; it does not overwrite the prior price or stock.
- Preserve original `price`, `shipping`, `currency`, `condition`, availability,
  verification status, field evidence and failures as returned by the research
  contract. Reject nonfinite, fractional or out-of-range JPY values at the
  planner adapter; do not round or silently coerce them.
- `ResearchReport` v1 uses float annotations for prices. The shared money policy
  is integer JPY: the adapter accepts only mathematically integral, valid JPY
  amounts. A future wire-type change needs an explicit contract revision.
- Save source text and its exact hash under `data/evidence/`. Include an evidence
  manifest in the run linking each report evidence hash/URL/time to the saved
  file. Unavailable evidence remains an explicit failure, not a fabricated file.
- Retrieval time is when we fetched the content. It does not establish when an
  indexed price was current. Keep `indexed_snippet`, `extracted_page` and
  `verified_listing` semantics from the research contract.
- `comparable_offers` and lowest-price fields are derived views of `listings`.
  They must refer to the same observations; no independent mutable price list.
- Finalize partial/failed runs with the observations and failures already known.
  For an interrupted run, retain its journal and mark it interrupted; do not
  manufacture a completed report.

Research can find a card without owning it. Research must never insert or alter
an owned-copy record, change sale permission or update confirmed cash.

## Decision, action and cash lifecycle

Persist the immutable decision artifact before preparing an action. Its input
references include exact research runs/observations, goal version and collection
snapshot/revisions. Until revisioned snapshots exist, save the exact input
snapshot with the decision; referencing only today's mutable collection is
insufficient. Draft revisions similarly retain their confirmed facts.

The collection/trading persistence layer owns action intents, reservations,
ownership events and cash events in SQLite. These are additive production
records; the existing `fixture_actions` table is exclusively a test ledger and
must not be relabeled as a live trading ledger.

| Event | Storage effect |
| --- | --- |
| Image identified | Save a candidate and evidence; no owned copy yet. |
| User confirms possession | Create one owned copy with its confirmed snapshot. |
| Research or recommendation | Save evidence/report/decision; no ownership or cash change. |
| Action prepared | Persist an immutable intent; atomically reserve cash or an eligible copy when applicable. |
| Buy order confirmed | Record the order as confirmed/pending receipt; do not claim the physical card is already held. |
| Purchased card received and confirmed | Create/link the owned copy using the order/receipt; prevent duplicate registration. |
| Sell listing published | Link the listing to the copy; keep ownership and its sale reservation. |
| Sale accepted, unsettled | Record the pending transfer/proceeds; do not credit spendable cash. |
| Transfer completed / cash settled | Record these independently; transfer ends ownership, settlement credits confirmed cash. |
| Submission outcome unknown | Retain reservations and reconcile the same intent. |
| Action definitively failed/cancelled | Release only the reservations that can safely be released; preserve its event history. |

Confirmed cash is a currency-scoped ledger balance, not a sum of collection
valuations or proposed sale proceeds. Opening balances need an explicit user
entry. Record debits, credits, settlement references and corrective events with
unique event IDs. Do not invent a cash balance for legacy collection records.

Reservations and corresponding state changes must commit in the same SQLite
transaction. Stable intent/event IDs make replay idempotent. New collection or
cash events create a new revision; earlier evidence and decisions remain intact.
Use foreign-key checks for new relational records and require explicit schema
migrations; do not drop/recreate existing tables to adopt this contract.

## Ownership and implementation order

| Workstream | Writes | Reads |
| --- | --- | --- |
| Intake/collection | Candidates, confirmed copies, image registry, condition history | Confirmed user input and intake evidence. |
| Research | Research requests, events, evidence and reports | Confirmed target and research limits. |
| Decision | Decision artifacts | Goal, collection/cash snapshots and research reports. |
| Trading/ledger | Drafts, intents, reservations, verified action/ownership/cash events through the persistence API | Decision, confirmed copy facts and fresh action evidence. |

For the hackathon, preserve the current `Collection` API and database first.
Then implement image retention and condition evidence, persist research reports,
and add an explicit research-to-planner adapter. Keep fixture execution visibly
separate. Implement production lifecycle/cash tables only when that path is
needed; unsupported operations must remain unavailable rather than pretending
this document made them operational.
